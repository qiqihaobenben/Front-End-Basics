# Cursor 使用

## 好的实践

- 在提示中要具体。像编写微型规格说明一样，详细说明技术栈、行为和约束条件。
- 按文件逐个处理；在小范围内、专注地生成、测试和审查。
- 先编写测试，锁定它们，然后生成代码，直到所有测试都通过。
- 使用 @ file、@ folders、@ git 来让 Cursor 的注意力集中在代码库的合适部分。
- 将设计文档和清单保存在 .cursor/ 中，以便代理对下一步该做什么有完整的上下文。
- 有目的地选择模型。Gemini 用于精确，Claude 用于广度。
- 将 Cursor 代理视为一位强大的初级助手——只要指引好方向，它就能快速高效地完成任务。
- 在开始时设定 5-10 条清晰的项目规则，以便 Cursor 了解你的结构和约束。尝试为现有代码库使用/generate rules。

## Cursor rules

### 概览

Cursor Rules 系统不仅仅是为 AI 提供简单指令的工具，而是一套为大型语言模型（LLM）提供“持久化上下文”的核心机制 。传统上，LLM 在每次交互后都会丢失记忆，导致开发者不得不反复输入相同的背景信息、编码偏好或项目规范。规则系统通过在每次启动聊天（Chat）或内联编辑（Inline Edit）时，将预先定义的指令内容注入到模型上下文中，为 AI 提供了稳定的、可复用的“系统提示”（System Prompt）。这种机制从根本上改变了开发者与 AI 的协作模式，使 AI 的行为更加一致、可预测和高效。

将规则视为代码库的“架构契约”（Architectural Contract）是一种更为深刻的理解。规则系统的真正价值在于它将 AI 的行为从“个人偏好”提升到了“项目标准”的层面。通过将规则文件.mdc 存储在项目目录的.cursor/rules 中并进行版本控制（Git），规则不再是单个人在 Cursor 设置中的私有配置，而是成为团队共同维护的、可追踪的、强制性的项目文档 。这意味着新成员入职时，只需克隆仓库，Cursor 规则便会自动生效，无需口头或文档说明，极大地加速了团队的入职（Onboarding）流程，并保证了 AI 在整个团队中的行为一致性 。这解决了传统 AI 辅助工具中，每个开发者都有自己一套 Prompt 和习惯，导致 AI 输出不一致的问题。

Cursor 的规则系统演进至今，形成了包含三大核心类型的现代体系：

#### 项目规则（Project Rules）：

这是当前官方推荐的核心方案。项目规则存储在项目根目录下的.cursor/rules 目录中，是版本可控的，并且其作用域限定在当前代码库 。这种类型允许开发者根据不同规则文件设置不同的触发条件，如文件路径、AI 请求意图等，从而实现对 AI 行为的细粒度控制。

#### 用户规则（User Rules）：

这是一种全局性的个人偏好配置。用户规则通过 Cursor 的 Settings 界面进行配置，以纯文本形式存在，并且始终应用于用户的 Cursor 环境中的所有项目 。它适用于设置个人编码风格、沟通偏好或通用的最佳实践，例如“请使用简洁的风格回复，避免不必要的重复” 。

#### 遗留规则（Legacy.cursorrules）：

这个位于项目根目录的单一文件是旧版 Cursor 的规则载体 。尽管仍被支持，但它已被正式弃用，官方强烈建议所有用户迁移到新的项目规则体系 。

旧版 .cursorrules 文件的弃用并非偶然，而是 Cursor 从个人效率工具向团队协作工具演进的必然结果。旧的单一文件模式限制了规则的模块化、组织和共享。当项目变得复杂时，一个单一文件会变得臃肿、难以管理和阅读 。

而新的 .cursor/rules 目录结构则允许按功能、模块或文件类型拆分规则，从而提高了可读性、可维护性和协作效率，使其真正具备了处理大规模、复杂项目的能力。

### 存放位置

项目规则的正确构建和存放是确保其有效性的先决条件。

所有项目规则文件都必须存放在项目的.cursor/rules 目录中 。Cursor AI Agent 仅会识别和应用此目录及其子目录下的规则文件，这是硬性的位置要求。这一设计解决了旧版 .cursorrules 文件必须位于项目根目录的局限性，使得规则可以与代码库的特定部分更紧密地关联起来。

为了有效组织规则，Cursor 支持在.cursor/rules 目录内部创建嵌套子目录，以实现规则的层级化组织 。例如，在单体应用中，可以将规则按功能或技术栈划分，将前端规则、后端规则、数据库规则分别放入不同的子目录。对于单仓多项目（Monorepo）的复杂结构，可以在每个子项目的根目录（例如，frontend/.cursor/rules 或 backend/server/.cursor/rules）创建独立的规则目录 。这样，当开发者在特定子项目下工作时，只有与其相关的规则会被自动附加，从而避免了不必要的上下文开销。

### 编写规则

Cursor Rules 主要采用 **.mdc** (Markdown-based) 文件格式，通常放置在项目根目录的 `.cursor/rules` 目录下。

#### 1. Rules 文件类型与结构

一个典型的 `.mdc` 规则文件包含两部分：**元数据（YAML 格式）**和**规则内容（Markdown 格式）**。

元数据控制规则如何被应用，而内容则提供具体的指导。

- 元数据部分：
  - Description: 规则的描述，不仅仅是简单的描述，对于 RuleType 为 “Agent Requested”类型的规则而言，它是 AI 决定是否应用该规则的唯一依据 。AI 会根据用户输入的 Prompt，结合所有可用规则的 Description 字段，自主决定是否将特定规则添加到上下文中 。
  - Globs: 定义此规则适用的文件模式（可选，取决于 RuleType），字段用于定义文件模式，确保“Auto Attached”规则仅在匹配的文件被引用时才生效 。这使得规则能够实现上下文感知，例如，仅当处理 `*.tsx` 文件时，才应用 React 组件相关的规则。
  - RuleType: 规则类型，有四种类型：Always、Auto Attached、Agent Requested、Manual。下面有详细介绍。
- 规则内容部分：
  - 具体的规则描述，使用 Markdown 语法。规则的内容应像清晰、简洁的内部技术文档，提供高层次的概述、具体代码示例、核心原则和常见陷阱 。好的规则内容不应过于模糊或冗长，应聚焦于具体的、可操作的指令 。

```mdc
---
# 元数据部分
Description: 这里填写规则的描述，例如“Java 编码规范”
Globs: "**/*.java" # 定义此规则适用的文件模式（可选，取决于RuleType）
RuleType: Auto Attached # 规则类型
---

# 规则内容部分
以下是具体的规则描述，使用 Markdown 语法。

## 命名规范
- 类名使用 `PascalCase`
- 方法名和变量名使用 `camelCase`
- 常量使用 `UPPER_SNAKE_CASE`

## 代码风格
- 使用 4 个空格进行缩进
- 禁止使用 `any` 类型（TypeScript 项目）
- 公有方法必须包含 JSDoc 注释

## 项目结构
- Controller 层不应包含业务逻辑
- 使用统一的响应体封装格式
- ... （其他你希望的约束条件）
```

#### 2. Rules 的四种类型

在元数据中，`RuleType` 定义了规则的应用方式：

| 规则类型 (RuleType) | 含义与应用场景                                                                                                                                                                                                                                                                            | 示例                                                                         |
| :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------- |
| **Always**          | **始终启用**：适用于定义项目核心原则和技术栈 。此类型的规则始终被包含在模型上下文中，与当前正在编辑的文件或用户的 Prompt 无关。其主要用途是强制性的架构模式、核心技术栈（如“使用 React 和 TypeScript”）以及代码质量标准（如“通过 ESLint 检查”）。                                         | 项目通用的代码风格、目录结构要求。                                           |
| **Auto Attached**   | **按文件自动关联**：当操作特定类型的文件时自动生效。当用户引用或编辑一个符合 globs 模式的文件时，此规则会自动附加到 AI 的上下文中 。它非常适用于为特定模块或文件类型定义模式，例如针对 `frontend/**/*.tsx`文件自动附加 React 组件规范，或针对`backend/**/*.py`文件自动附加后端服务模式 。 | 例如：`Globs: "**/*.tsx"` 时，在处理 React TSX 文件时自动应用此规则。        |
| **Agent Requested** | **Agent 智能调用**：由 AI 根据任务描述智能判断是否采用。必须提供清晰的 `Description`。                                                                                                                                                                                                    | 描述为“Django 模型规范”，当任务涉及创建 Django 模型时，AI 可能会主动使用它。 |
| **Manual**          | **手动引用**：仅在用户明确提及（例如使用@ruleName 语法）时才生效 。此类型适用于特定且不常用的复杂工作流，如数据库迁移、项目脚手架生成或特定的部署步骤。                                                                                                                                   | 一些不常用或特定场景的规则，如 `@git.mdc`。                                  |

#### 3. 规则内容编写要点

编写规则内容时，可以涵盖以下方面：

- **技术栈指定**：明确项目使用的语言、框架、库及其版本。
- **代码风格**：缩进、空格、换行、分号、引号等格式要求。
- **命名规范**：变量、函数、类、文件、目录的命名约定。
- **架构与模式**：项目结构（如 MVC、DDD）、设计模式的使用、层与层之间的职责划分。
- **安全与最佳实践**：禁止的不安全函数、输入验证、密码处理、依赖管理等。
- **文档与注释**：要求公共 API、复杂逻辑等必须有注释，并规定注释格式。
- **测试**：测试框架、命名规范、覆盖率要求等。

#### 4. 规则的分层与组织

对于大型项目，建议将规则拆分到不同文件中，分层次管理：

```
.cursor/
└── rules/
    ├── core.mdc                 # Always类型，最核心的规范
    ├── tech-stack.mdc          # 技术栈定义
    ├── project-structure.mdc   # 项目目录结构
    ├── java.mdc                # Auto Attached, Glob: **/*.java
    ├── spring-boot.mdc         # Agent Requested, SpringBoot相关规范
    ├── react.mdc               # Auto Attached, Glob: **/*.tsx
    └── git.mdc                 # Manual类型，Git提交规范等
```

在规则文件中，可以通过 `@filename.mdc` 引用其他规则文件的内容。

#### 5. 编写原则（MSEC 理论）

- **M (Minimization) - 最小化原则**：规则应**简洁、专注**，避免冗长和模糊。大而全的模糊指令效果往往不好，且会消耗更多 Token。
- **S (Structured) - 结构化原则**：采用**分层架构**（通用、语言、框架、其他）管理规则，清晰明了。
- **E (Explicitness) - 精准引用原则**：明确告诉 AI 该使用哪些规则（`@规则名`）或参考哪些代码文件（`@文件路径`）。
- **C (Consistency) - 一致性原则**：规则本身和生成的代码都应保持**风格和标准的一致性**。

### 生成 Cursor Rules (Generate Rules)

创建规则文件可以从零开始手动编写，也可以利用工具或 AI 生成初始模板。

#### 1. 让 AI 生成初始规则

最快捷的方式是**直接让 Cursor 中的 AI 帮你创建**。你可以提供一个高层次的描述。

> **示例提示词 (Prompt)**：
> “我现在想开发一个前后端分离的后端项目，请使用 Java 语言，项目从零开始开发。请帮我生成一个 Cursor 中的 Rules 规则文件（markdown 格式），能够让我们的后端项目按照现代化规范流程进行功能实现，请尽可能的完整。”

AI 可能会生成一个包含项目结构、编码规范、依赖管理等内容的初始规则文件，你可以在此基础上修改和细化。

#### 2. 使用规则生成器工具

有一些社区或官方提供的工具可以帮助生成规则：

- **epoint-mrules-generator**: 一个 npm 命令行工具，可为特定环境（如 M8 跨端框架）快速生成预定义的规则文件集（如 `M8.mdc`, `vue.mdc`等）。
  ```bash
  # 安装
  npm install -g epoint-mrules-generator
  # 在项目根目录运行 (for Cursor)
  epoint-mrules --type cursor
  ```
- **在线生成器**: 一些网站提供基于 Gemini 等大模型的在线 Rules 生成服务，你只需选择项目类型和技术栈。

#### 3. 迭代优化你的规则

规则不是一成不变的。一个非常好的实践是：

1.  **初步生成**：让 AI 生成一个基础版本的规则。
2.  **实践检验**：在开发第一个功能模块时应用这些规则。
3.  **反思优化**：让 Cursor **分析和反思**已完成的模块代码，并提出对规则的优化建议。
4.  **更新迭代**：根据 AI 的建议和你自己的判断，**更新和补充**规则文件。
5.  **循环往复**：在后续开发中不断重复此过程，使规则越来越完善和精准。

### 简单的例子

假设有一个 React TypeScript 项目，可以创建 `react.mdc`：

```mdc
---
Description: React with TypeScript 开发规范
Globs: "src/**/*.tsx"
RuleType: Auto Attached
---

# React TypeScript 规范

## 组件规范
- 优先使用函数组件和 Hooks。
- 组件命名使用 `PascalCase`。
- Props 必须使用 `interface` 或 `type` 明确定义。

## 状态管理
- 使用 `useState` 进行本地状态管理。
- 复杂状态逻辑考虑使用 `useReducer`。

## 代码风格
- 使用箭头函数定义组件。
- 默认使用 `const` 声明变量和函数。
- 界面组件代码与样式分离。

@core.mdc # 引用核心通用规则
```

### 注意事项

1.  **规则可能不生效**：检查规则文件的**位置**（`.cursor/rules/`）、**格式**（尤其是元数据的拼写和缩进）以及 **Globs 模式**是否正确匹配目标文件。
2.  **Token 消耗**：规则内容会占用每次 AI 请求的 Token 数量。遵循**最小化原则**，只保留必要规则。
3.  **规则冲突**：如果多个规则文件定义了冲突的规则，AI 的行为可能不可预测。合理规划规则的范围和层次。
4.  **版本控制**：建议将 `.cursor/rules` 目录加入版本控制（如 Git），以便团队共享。

### 总结与对比

下表总结了四种规则类型的关键特点：

| 规则类型            | 控制方式     | 最佳适用场景                                           | 优点                       | 缺点                           |
| :------------------ | :----------- | :----------------------------------------------------- | :------------------------- | :----------------------------- |
| **Always**          | 全局自动     | 所有项目和文件都需遵守的**核心基础规范**               | 一劳永逸，强制统一         | 可能消耗较多 Token             |
| **Auto Attached**   | 文件类型自动 | 针对**特定语言或文件类型**的规范（如 `.js`, `.py`）    | 精准自动化，减少手动干预   | 需正确定义 Globs               |
| **Agent Requested** | AI 智能判断  | **框架、库或特定任务**的规范（如 Spring Boot, Django） | 灵活，由 AI 根据上下文决策 | 依赖清晰的描述，效果可能不稳定 |
| **Manual**          | 手动调用     | **不常用**或**非常具体场景**的规则（如 Git, 文档）     | 按需取用，不浪费 Token     | 需记住并手动引用               |
