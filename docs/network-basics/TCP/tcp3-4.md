# TCP 的三次握手和四次挥手

## 核心概念：为什么需要握手和挥手？

TCP 是一种**面向连接的、可靠的**传输层协议。这意味着在数据传输之前，通信双方必须首先建立一条连接，并在传输结束后礼貌地关闭它，以确保数据完整、有序地送达。

- **三次握手**：目的是为了**建立一条可靠的双向通信通道**。双方需要同步序列号，并确认对方的收发能力正常。
- **四次挥手**：目的是为了**安全可靠地关闭一条双向通信通道**。因为 TCP 连接是全双工的，每个方向必须独立关闭。

### TCP 三次握手

这个过程就像两个人打电话建立通话前的确认：

> **A：** “喂，听得到吗？我打算用序号 X 开始说话。”
> **B：** “听得到。我打算用序号 Y 开始说话。请确认你听到了这句。”
> **A：** “确认，我听到你了。那我们开始吧。”

**专业术语解释：**

在 TCP 报文头部有几个重要的控制位：

- **SYN**：同步序列号，用于发起一个新连接。
- **ACK**：确认（acknowledgement），表示确认号字段是有效的。
- **SEQ**：序列号（sequence number），标识发送的数据字节流。
- **ACK Num**：确认号，表示期望收到的下一个序列号。

**详细过程：**

1.  **第一次握手（SYN）**

    - **客户端** 向服务器发送一个 TCP 报文。
    - 设置 **SYN = 1**，表示这是一个握手连接请求。
    - 选择一个随机的初始序列号 **seq = x**。
    - 此时客户端进入 `SYN-SENT` 状态。

2.  **第二次握手（SYN + ACK）**

    - **服务器** 收到客户端的 SYN 报文后，如果同意连接，则会回复一个报文。
    - 设置 **SYN = 1**，表示这也是一个握手连接请求。
    - 设置 **ACK = 1**，表示这是一个确认报文。
    - 选择自己的一个随机初始序列号 **seq = y**。
    - 将 **ack = x + 1**（客户端的 seq + 1），表示已经收到了客户端的序列号 x，并期望下次从 x+1 开始接收。
    - 此时服务器进入 `SYN-RCVD` 状态。

3.  **第三次握手（ACK）**
    - **客户端** 收到服务器的 SYN-ACK 报文后，会再次向服务器发送一个确认报文。
    - 设置 **ACK = 1**。
    - 序列号 **seq = x + 1**（因为第一次握手的 SYN 消耗了一个序列号）。
    - 将 **ack = y + 1**（服务器的 seq + 1），表示已经收到了服务器的序列号 y，并期望下次从 y+1 开始接收。
    - 此包发送完毕后，**客户端和服务器都进入 `ESTABLISHED` 状态**，连接建立成功，可以开始传输数据了。

**为什么是三次，而不是两次？**

**核心原因：防止已失效的连接请求报文突然又传送到服务器，从而产生错误。**

考虑一个场景：

1.  客户端发送了一个 SYN 报文（请求 1），但由于网络拥堵，迟迟未到达服务器。
2.  客户端超时后重发了一个 SYN 报文（请求 2），这次成功建立连接并完成了数据传输，连接关闭。
3.  此时，那个失效的“请求 1”终于到达了服务器。服务器会认为这是一个新的连接请求，于是回复 SYN-ACK。
4.  如果只有两次握手，服务器只要收到 SYN 就进入 `ESTABLISHED` 状态，并开始等待客户端发送数据。但客户端并没有意图建立新连接，会忽略服务器的 SYN-ACK，导致服务器空等，浪费了资源。

**通过第三次握手**，客户端不会对那个失效的 SYN-ACK 进行确认，服务器收不到确认，就不会建立连接。这就避免了服务器资源的浪费。

### TCP 四次挥手

这个过程就像两个人通完话后礼貌地结束对话：

> **A：** “我要说的话都说完了，我准备挂电话了。”
> **B：** “好的，我知道你说完了。”（此时 B 可能还有话要说）
> ... B 把最后的话说完 ...
> **B：** “我也说完了，我也准备挂电话了。”
> **A：** “好的，那我们挂吧。”

**专业术语解释：**

新增一个控制位：

- **FIN**：结束，表示发送方没有更多数据要发送，希望关闭连接。

**详细过程：**

假设客户端主动发起关闭。

1.  **第一次挥手（FIN）**

    - **客户端** 向服务器发送一个 TCP 报文。
    - 设置 **FIN = 1**，序列号 **seq = u**（u 等于客户端上次已传送数据的最后一个字节的序列号加 1）。
    - 此时客户端进入 `FIN-WAIT-1` 状态，表示客户端没有数据要发送了。

2.  **第二次挥手（ACK）**

    - **服务器** 收到 FIN 报文后，立即回复一个确认报文。
    - 设置 **ACK = 1**。
    - 确认号 **ack = u + 1**。
    - 序列号 **seq = v**。
    - 此时服务器进入 `CLOSE-WAIT` 状态。**TCP 连接处于半关闭状态**，即客户端到服务器的连接已经关闭，客户端不会再发送数据，但服务器到客户端的连接仍然开放，服务器可能还有数据要发送给客户端。
    - 客户端收到这个 ACK 后，进入 `FIN-WAIT-2` 状态，等待服务器的 FIN 报文。

3.  **第三次挥手（FIN）**

    - 当服务器也没有数据要发送时，它会发送一个 FIN 报文。
    - 设置 **FIN = 1**，同时通常也会 **ACK = 1**（因为要确认之前的所有数据）。
    - 序列号 **seq = w**（可能在第二次挥手后，服务器又发送了一些数据）。
    - 确认号 **ack = u + 1**（不变）。
    - 此时服务器进入 `LAST-ACK` 状态，等待客户端的最终确认。

4.  **第四次挥手（ACK）**
    - **客户端** 收到服务器的 FIN 报文后，会发送一个确认报文。
    - 设置 **ACK = 1**。
    - 序列号 **seq = u + 1**。
    - 确认号 **ack = w + 1**。
    - 此时客户端进入 `TIME-WAIT` 状态。**请注意，不是直接关闭，而是需要等待 2MSL（Maximum Segment Lifetime，报文最大生存时间）的时间后，才进入 `CLOSED` 状态。**
    - 服务器在收到这个 ACK 后，立即进入 `CLOSED` 状态。

**为什么需要四次挥手？**

因为 TCP 是全双工的，关闭连接需要两个方向独立进行。

- 第一次和第二次挥手：关闭了从客户端到服务器的通道。
- 第三次和第四次挥手：关闭了从服务器到客户端的通道。

服务器在收到客户端的 FIN 时，可能还有数据没发送完，所以不能将 FIN 和 ACK 合并在一起发送，这就是为什么需要四次挥手，而不是三次。

**为什么客户端最后需要 TIME-WAIT 状态，并等待 2MSL？**

1.  **可靠地终止连接**：确保客户端发送的最后一个 ACK 能到达服务器。如果这个 ACK 在网络中丢失，服务器会超时重传它的 FIN 报文。客户端在 `TIME-WAIT` 状态下可以收到这个重传的 FIN，并再次发送 ACK。如果没有这个等待，客户端直接关闭，服务器将永远收不到确认，无法正常关闭。
2.  **让旧连接的所有报文都消失**：等待 2MSL 时间，可以确保本次连接所产生的所有报文都在网络中消失，这样在建立下一个新连接时，就不会收到旧的、迟到的报文，从而避免数据混乱。

### 总结

| 过程         | 目的         | 核心步骤                 | 关键点                                                                                       |
| :----------- | :----------- | :----------------------- | :------------------------------------------------------------------------------------------- |
| **三次握手** | **建立连接** | SYN -> SYN-ACK -> ACK    | **防止失效的请求建立无效连接**，确保双方收发能力正常。                                       |
| **四次挥手** | **关闭连接** | FIN -> ACK -> FIN -> ACK | **全双工通道需要双向独立关闭**。**TIME-WAIT** 状态确保连接可靠终止，并让旧报文在网络中消逝。 |

## Wireshark 抓包示例

使用一个真实的 **HTTP 请求** 的 Wireshark 抓包示例，来一步步展示三次握手、数据传输和四次挥手。

### 场景设定

- **客户端 (Client)**: IP 地址为 `192.168.1.100`
- **服务器 (Server)**: IP 地址为 `34.107.221.82` (httpbin.org 的一个实例)
- **动作**: 客户端向服务器发送一个简单的 HTTP GET 请求，获取 `/json` 端点数据。

### 第一部分：三次握手

三次握手的目标是建立一个 TCP 连接。客户端使用一个随机的本地端口（本例中为 `59300`），连接服务器的 80 端口。

**抓包数据解读：**

| No. | 源地址        | 目标地址      | 协议 | 信息 (Info)                       | **Seq**      | **Ack** | **Flags**    |
| :-- | :------------ | :------------ | :--- | :-------------------------------- | :----------- | :------ | :----------- |
| 1   | 192.168.1.100 | 34.107.221.82 | TCP  | 59300 → 80 [SYN] Seq=0            | 0 (相对 Seq) |         | **SYN**      |
| 2   | 34.107.221.82 | 192.168.1.100 | TCP  | 80 → 59300 [SYN, ACK] Seq=0 Ack=1 | 0 (相对 Seq) | 1       | **SYN, ACK** |
| 3   | 192.168.1.100 | 34.107.221.82 | TCP  | 59300 → 80 [ACK] Seq=1 Ack=1      | 1            | 1       | **ACK**      |

**详细解释：**

1.  **第一次握手 (Packet 1):**

    - **动作**: 客户端发送一个 `SYN` 报文到服务器（标志位分别为 urg,ack,psh,rst,syn,fin，SYN 对应 02 十六进制转为二进制为 0000010）。
    - **Seq**: 客户端随机选择一个初始序列号 (实际值很长，Wireshark 为了方便显示为相对值 `0`)。
    - **含义**: “你好服务器，我想和你建立连接。我的初始序列号是 0。”

2.  **第二次握手 (Packet 2):**

    - **动作**: 服务器回复一个 `SYN-ACK` 报文。
    - **Seq**: 服务器也随机选择自己的初始序列号 (相对值 `0`)。
    - **Ack**: `1`。这是关键，它等于客户端的 Seq(0) + 1。意思是“我收到了你的 Seq=0，我期望你下次从 Seq=1 开始发送”。
    - **Flags**: 同时设置了 `SYN` 和 `ACK`。
    - **含义**: “收到你的连接请求了 (ACK)。我同意建立连接，我的初始序列号是 0 (SYN)。”

3.  **第三次握手 (Packet 3):**
    - **动作**: 客户端发送一个 `ACK` 报文。
    - **Seq**: `1`。因为第一个 SYN 包消耗了一个序列号。
    - **Ack**: `1`。这等于服务器的 Seq(0) + 1。意思是“我收到了你的 Seq=0，我期望你下次从 Seq=1 开始发送”。
    - **含义**: “好的，确认收到。我们现在可以开始通信了。”

**至此，TCP 连接建立成功，进入 `ESTABLISHED` 状态。**

---

### 第二部分：数据传输

连接建立后，应用程序（这里是 HTTP）开始发送数据。

**抓包数据解读：**

| No. | 源地址        | 目标地址      | 协议 | 信息 (Info)                        | **Seq** | **Ack** | **Flags** | 长度 |
| :-- | :------------ | :------------ | :--- | :--------------------------------- | :------ | :------ | :-------- | :--- |
| 4   | 192.168.1.100 | 34.107.221.82 | HTTP | GET /json HTTP/1.1                 | 1       | 1       | **ACK**   | 129  |
| 5   | 34.107.221.82 | 192.168.1.100 | TCP  | 80 → 59300 [ACK] Seq=1 Ack=130     | 1       | 130     | **ACK**   | 0    |
| 6   | 34.107.221.82 | 192.168.1.100 | HTTP | HTTP/1.1 200 OK (application/json) | 1       | 130     | **ACK**   | 311  |
| 7   | 192.168.1.100 | 34.107.221.82 | TCP  | 59300 → 80 [ACK] Seq=130 Ack=312   | 130     | 312     | **ACK**   | 0    |

**详细解释：**

- **Packet 4**: 客户端通过已建立的 TCP 连接发送 HTTP 请求。`Seq=1, Ack=1`。这个数据包携带了 129 字节的 HTTP 数据。
- **Packet 5**: 服务器确认收到了 HTTP 请求。`Ack=130`。这个数字是 `客户端的Seq(1) + 数据长度(129) = 130`，表示“我已收到你 Seq=1 开始的 129 字节数据，期望你下次从 Seq=130 开始发送”。
- **Packet 6**: 服务器发送 HTTP 响应。`Seq=1` (服务器端的序列号)，`Ack=130`。这个数据包携带了 311 字节的 JSON 数据。
- **Packet 7**: 客户端确认收到了 HTTP 响应。`Ack=312`。这个数字是 `服务器的Seq(1) + 数据长度(311) = 312`，表示“我已收到你的全部响应数据”。

---

### 第三部分：四次挥手

数据传输完毕，任何一方都可以发起关闭连接。这里由**客户端**主动发起关闭。

**抓包数据解读：**

| No. | 源地址        | 目标地址      | 协议 | 信息 (Info)                           | **Seq** | **Ack** | **Flags**    |
| :-- | :------------ | :------------ | :--- | :------------------------------------ | :------ | :------ | :----------- |
| 8   | 192.168.1.100 | 34.107.221.82 | TCP  | 59300 → 80 [FIN, ACK] Seq=130 Ack=312 | 130     | 312     | **FIN, ACK** |
| 9   | 34.107.221.82 | 192.168.1.100 | TCP  | 80 → 59300 [ACK] Seq=312 Ack=131      | 312     | 131     | **ACK**      |
| 10  | 34.107.221.82 | 192.168.1.100 | TCP  | 80 → 59300 [FIN, ACK] Seq=312 Ack=131 | 312     | 131     | **FIN, ACK** |
| 11  | 192.168.1.100 | 34.107.221.82 | TCP  | 59300 → 80 [ACK] Seq=131 Ack=313      | 131     | 313     | **ACK**      |

**详细解释：**

1.  **第一次挥手 (Packet 8):**

    - **动作**: 客户端发送 `FIN-ACK` 报文。
    - **Seq**: `130`, `Ack`: `312`。这是延续数据传输阶段的序列号。
    - **Flags**: `FIN` 和 `ACK`。
    - **含义**: “我没有数据要发送了，请求关闭我到你方向的连接。”

2.  **第二次挥手 (Packet 9):**

    - **动作**: 服务器回复 `ACK` 报文。
    - **Ack**: `131`。这是 `客户端的Seq(130) + FIN标志占用的1 = 131`。
    - **含义**: “我同意关闭你到我方向的连接。” 此时，**客户端到服务器的连接已关闭**。客户端进入 `FIN-WAIT-2` 状态。但服务器可能还有数据要发（虽然这里没有），所以连接处于**半关闭**状态。

3.  **第三次挥手 (Packet 10):**

    - **动作**: 服务器也发送 `FIN-ACK` 报文。
    - **Seq**: `312` (延续之前的)，`Ack`: `131`。
    - **含义**: “我这边也没有数据要发送了，请求关闭我到你这个方向的连接。”

4.  **第四次挥手 (Packet 11):**
    - **动作**: 客户端回复最终的 `ACK` 报文。
    - **Ack**: `313`。这是 `服务器的Seq(312) + FIN标志占用的1 = 313`。
    - **含义**: “我同意关闭。” 客户端发送此包后进入 `TIME-WAIT` 状态，等待 2MSL 后彻底关闭。服务器收到此 ACK 后立即关闭连接。

### 总结

这个抓包完美地展示了 TCP 连接的生命周期：

1.  **建立连接**: `[SYN] -> [SYN, ACK] -> [ACK]`
2.  **传输数据**: `[PSH, ACK] -> [ACK]` (应用数据在 `PSH` 包中)
3.  **断开连接**: `[FIN, ACK] -> [ACK] -> [FIN, ACK] -> [ACK]`

通过这个实际的例子，你可以清晰地看到序列号 (`Seq`) 和确认号 (`Ack`) 是如何递增的，以及 `SYN`, `ACK`, `FIN` 这些标志位在何时被设置。这正是 TCP **可靠性**和**有序性**的体现。
